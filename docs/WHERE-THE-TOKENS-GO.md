# Where the tokens go

This page documents the benchmark data already in
[`bench/results/`](../bench/results); it needs no new runs. Every table on it
is generated by [`bench/docs.mjs`](../bench/docs.mjs) from the raw run files
listed under [Sources](#sources), and CI fails if one drifts from them. The runs
are the ones in the [README](../README.md#benchmark).

## Tokens are not cost

Claude Code reports four kinds of tokens for each run, and they are priced very
differently. A kind of token's share of all tokens says little about its share
of the cost.

prices each kind of token at its list price:

Prices are USD per million tokens, from Anthropic's
[pricing page](https://platform.claude.com/docs/en/about-claude/pricing), as
used in [`bench/lib/pricing.mjs`](../bench/lib/pricing.mjs). Cache writes are
priced at the 1-hour rate, twice the input price, because that is what Claude
Code writes: the last three columns show that each run's recorded
`total_cost_usd` equals its token counts priced this way. At the 5-minute rate
(1.25 times the input price) the sums do not match. `total_cost_usd` is Claude
Code's own estimate at API list prices, not an invoice.

## Context is paid twice

A token that enters the context is paid once when it is written to the cache,
and again, at the cache-read price, on every later turn that sends the
conversation back. For N tokens that enter on turn k of a run of T turns:

```
cost ≈ N × cache-write price + N × cache-read price × (T − k)
```

<!-- TWICE:START -->
| Model | Median turns, baseline run | Cache write | Cache read | Write ÷ read | Write share of a turn-1 token |
| --- | ---: | ---: | ---: | ---: | ---: |
| Opus 5.5 | 11.5 | $8 | $0.2 | 40× | 79.2% |
| Sonnet 5 | 8 | $4 | $0.2 | 20× | 74.1% |
| Haiku 4.5 | 36.5 | $2 | $0.1 | 20× | 36.0% |
<!-- TWICE:END -->

The last column is the write's share of what one token costs over a median
baseline run when it enters on the first turn. Where runs are short, most of
that cost is the write; where they are long, the re-reads take over. Three
consequences:

- Keeping content out of the context lowers both the cache-write and the
  cache-read part of the bill.
- The agent's own output is billed at the output price and then becomes part
  of the context on the next turn, so it is also written and re-read.
- A change that saves tokens but adds a turn can cost more than it saves: the
  extra turn reads everything already in the context again.

Turns here are Claude Code's `num_turns`, the top-level agent loop.

## Runs that did not finish

Claude Code stops a run at the turn limit (`--max-turns 40`) and reports it as
`error_max_turns`. A stopped run did not finish the task, so its token count is
set by the limit, not by the work, and is not comparable with a finished run's.
A run that fails the hidden check can also stop early and look cheap. Every
figure below is the sum of per-task medians over the tasks that keep at least
one run in both conditions, with the number of tasks in parentheses.

<!-- QUALITY:START -->
| Model | Stopped by the turn cap | Of those, baseline runs that passed | Failed the hidden check | Tokens, all runs (tasks) | Passing runs only | All runs, same tasks as passing | Finished runs only |
| --- | :---: | :---: | :---: | ---: | ---: | ---: | ---: |
| Opus 5.5 | 0/16 → 0/16 | – | 0/16 → 0/16 | −15.8% (8) | −15.8% (8) | −15.8% (8) | −15.8% (8) |
| Sonnet 5 | 0/24 → 0/24 | – | 0/24 → 0/24 | −13.2% (8) | −13.2% (8) | −13.2% (8) | −13.2% (8) |
| Haiku 4.5 | 7/16 → 3/16 | 6/7 | 2/16 → 3/16 | −23.0% (8) | −18.8% (7) | −17.8% (7) | −26.5% (6) |
<!-- QUALITY:END -->

Where every run finished and passed, every column is the same. Where they are
not, compare them: keeping only passing runs drops any task in which one
condition never passed, and the "same tasks" column shows how much of the
change comes from dropping that task rather than from the runs excluded inside
the others. A stopped run is not always a failed one; the third column counts
the stopped baseline runs that still passed.

Every result is reported with this cross-check. A saving that shrinks when
stopped or failed runs are left out is partly an artifact of not finishing the
work, and is reported as such.

## What this does not show

- The rules and the hook thresholds were tuned on these same 8 tasks, so every
  figure is in-sample, and therefore optimistic.
- Eight tasks in two repositories, both command-line argument parsers (click in
  Python, commander.js in JavaScript), with two or three runs per task and
  condition. The 95% intervals in the README resample the tasks only; the
  run-to-run noise inside a task is folded into its median.
- Cost is Claude Code's estimate at API list prices, not an invoice. On a
  subscription the same work is paid in usage limits.
- Token counts depend on the model version, the Claude Code version and its
  system prompt, the tools that are enabled, and the task. Other workloads
  will differ.
- The replay in the README counts characters of tool output, not tokens, and
  only replays calls that don't change the repository.
